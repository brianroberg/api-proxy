Branch `test-audit-2026-09-24`, base `128be52` (main, PR #17 merge). Run by Claude (Opus 5.5) with workflow subagents
on the same model. This PR changes **tests only**. No production code is touched.

> **Status of this report: final.** The audit covered 5 module groups: 64 raw findings, 55 distinct once cross-group
> duplicates are merged. The fixes are committed. An independent verification pass is also complete. It used four
> agents (Opus 5.5, effort `high`), one per group, none of which wrote a finding or a fix. **All 47 Medium+ findings
> were reproduced at the base.** Six were re-graded: five Medium to Low, and one High to Medium. Of the 21 fix

## 1. Executive summary

**Confidence before this audit: low where it matters most.** The suite looked healthy: 324 tests, 77% branch
coverage, deterministic across 10 shuffled orders and two extreme timezones, with good unit coverage of the pure
pieces. But **every Critical finding was the same shape: the path production actually runs was never exercised.**

1. **The deployed approval mode was untested end to end.** Production starts with `--web-confirm` and no mode
   flag. Nothing tested the step from flags to mode: the default could become "no approval" (`NONE`) with the suite
   green. And the web branch of `ConfirmationHandler.confirm`, the path every gated write takes, never ran: a
   handler that approved everything, including operator rejections, passed all 324 tests.
2. **Trash and untrash could skip approval.** Every Gmail handler test ran with confirmation off and never fixed
   the upstream HTTP method, so mislabelling trash as a label change (no prompt), sending it as `GET`, or dropping
   a modify's body all passed.
3. **The calendar attendee block had no test that could fail.** The one test sending attendees also got its 403
   from the operator rejecting it. On an approval-exempt calendar (#16) that block is the only guard against the
   agent sending invitations. Id validation, which stops `event1?sendUpdates=all` (sent as `%3F`) from slipping
   past the #16 carve-out, was never exercised either.
4. **Stated invariants had no tests:** the keys file reloads per request (so revoke is a kill switch), errors never
   leak keys, blocked operations never prompt (the blocklist was only ever hit by POSTs the allowlist also
   rejects), and the key-management CLI had 0% coverage.
5. **Four production bugs filed** (sections 4 and 3): a revoke or disable can be undone by an in-flight request
   (api-proxy #19); a cancelled approval wait leaves an orphaned queue entry (#20); draft delete and calendar event
   delete answer 204 with a `null` body (#21); a `#` in a calendar id truncates the upstream URL (#22).

## 2. How the audit was run

- **Phase 1:** baseline green; branch coverage; CI runs `pytest -q` and `ruff` on every push with no markers or
  exclusions. The critical modules below drove sampling and severity.
- **Phase 2:** five auditor agents, each in its own git worktree, covered the gate (middleware, auth, keys CLI),
  the approval path (confirmation, web queue, dashboard, ntfy), Gmail, Calendar, and infrastructure (fixtures,
  flake hunt, regression history). They mutated production code to test the tests. No request was sent to any
  running proxy; all probes used TestClient, pytest-httpx or `httpx.MockTransport`.
- **Phase 3:** the fixes were written by the coordinating session in priority order, one commit per finding group.
  Each commit states the problem, the evidence and the verification. Before committing, every recorded mutation was
  re-applied to show the new test fails on the bug and passes on the real code.
- **Independent verification:** four further agents (Opus 5.5, effort `high`), one per module group, reproduced each
  Medium+ finding at the base and attacked each fix at the head of the first round (`017fdab`). The weak fixes were
  then strengthened in `cae48e8`, `b41abd5`, `c54ded7` and `84ff213`, and the verifier's surviving variants were
  re-applied against them (section 3a).

**Critical modules:** the allowlist/blocklist middleware; API-key auth and the keys file; the approval path (mode
wiring, handler→queue, dashboard stream, ntfy content); calendar mutation gating and the #16 exemption; Gmail
trash/modify/draft gating; the key-management CLI.

## 3. Findings

Severity: **Critical** = false confidence about something important, or important behaviour untested. Status: *Fixed
in `<commit>`* / *Documented only* (with the reason) / *Production bug, filed*. Each commit message carries the full
evidence for its fix.

### E. Suite-level structure (coordinator's assessment)

- **Balance.** The unit tests of pure pieces (`requires_confirmation`, `describe_request`, the queue methods,
  `build_rsvp_attendees`) are good. The gaps sat at the seams: main() → config, handler → queue, route →
  confirmation, proxy → upstream request. The new tests are mostly seam tests with a spec'd backend mock or
  pytest-httpx recording the real upstream request.
- **Test infrastructure explained several gaps.** Process-wide singletons (the confirmation handler, the web
  queue, the cached Gmail and Calendar clients, the mounted approval router) were never reset. As a result the
  valuable tests (web-confirm wiring, backend-auth failure) could not be written without order-dependent results.
  This PR adds autouse resets for all of them.
- **Mocks too loose to fail.** Handler tests use bare `AsyncMock()`s and pytest-httpx responses without a method, so
  wrong keyword names and wrong HTTP methods passed. The new tests use `create_autospec(CalendarClient)` and
  method-specific responses. Converting the existing handler tests is left as a follow-up (CAL-07).
- **Quality gates:** none beyond "tests pass" and ruff: no coverage threshold, no network guard (G1-07: a
  validation regression sent real requests to Google with fixture credentials), no per-test timeout.
